## 1. Пул соединений: 5 и очистка старых

### 1.1. Что есть сейчас (факты из кода)

- `database.py`: `pool_size=DB_POOL_SIZE`, `max_overflow=DB_MAX_OVERFLOW`, `pool_pre_ping=True`, `pool_recycle=1800`, `pool_use_lifo=True`, `application_name="billing_control"`.
- `config.py`: валидатор не даёт `pool_size + max_overflow > DB_CONNECTION_BUDGET`. Это хорошо, оставляем.
- `.env` (прод): `DB_POOL_SIZE=2`, `DB_MAX_OVERFLOW=0`, `DB_CONNECTION_BUDGET=2`.
- `Dockerfile`: uvicorn **без `--workers`**, то есть один процесс. Итоговый лимит соединений с БД = размер пула.
- `main.py` lifespan: на остановке уже вызывается `engine.dispose()`.
- `hard_start.sh`: `build`, затем `down --timeout 30`, затем `up`. Старый контейнер гасится **до** старта нового, поэтому пулы двух версий одновременно не живут.

### 1.2. Откуда на самом деле берутся «зависшие» соединения при обновлении

`engine.dispose()` на штатной остановке закрывает только **свободные** соединения пула. Остаются три дыры:

1. **Жёсткое убийство / падение хоста.** Если запрос не успел завершиться за 30 с, Docker шлёт SIGKILL, и lifespan не выполняется. *Уточнение по итогам проверки:* при SIGKILL/OOM процесса ядро само закрывает его сокеты и сервер БД это видит — реальные «сироты» появляются при падении/перезагрузке хоста и обрыве сети (п. 3).
2. **Занятые соединения**, которые в момент остановки обслуживают запрос, `dispose()` не закрывает.
3. **Полуоткрытые TCP-соединения** через NAT или облачную сеть. PostgreSQL узнаёт о смерти клиента только по TCP keepalive, а это по умолчанию около 2 часов.

В итоге на управляемом PostgreSQL копятся «мёртвые» сессии `billing_control` и съедают `max_connections`.

### 1.3. Решение: три уровня защиты

**Уровень 1: корректное завершение (почти бесплатно)**
- В `CMD` uvicorn добавить `--timeout-graceful-shutdown 20`. Тогда uvicorn сам завершит запросы за 20 с, до SIGKILL от compose (30 с), и `engine.dispose()` в lifespan гарантированно отработает.
- Писать в лог перед и после `dispose()` снимок пула (`pool_snapshot()` уже есть).

**Уровень 2: «уборщик» при старте, `reap_stale_connections()`**

Вызывается в lifespan **первым действием**, до `create_all` и `ensure_schema`. Делает один запрос:

```sql
SELECT pid, state, backend_start, pg_terminate_backend(pid) AS terminated
FROM pg_stat_activity
WHERE application_name = :app_name          -- 'billing_control:prod'
  AND usename = current_user
  AND pid <> pg_backend_pid()
  AND backend_start < :process_started_at   -- только соединения, открытые ДО старта этого процесса
  AND (
        state IN ('idle', 'idle in transaction', 'idle in transaction (aborted)')
     OR (state = 'active' AND query_start < now() - make_interval(secs => :stale_active_s))
  );
```

Правила безопасности уборщика:
- **Только своё имя приложения и своя роль БД.** Сессии `psql`, pgAdmin, бэкапов и других сервисов не трогаются.
- **`application_name` с окружением.** Сейчас везде просто `billing_control`, поэтому dev-бэкенд с ноутбука, подключённый к проду, неотличим от прода. Нужна новая переменная `APP_INSTANCE` (`prod` / `dev`), и тогда `application_name = f"billing_control:{APP_INSTANCE}"`.
- **Активные запросы не трогаются**, если им меньше `2 × DB_COMMAND_TIMEOUT` (60 с): живой запрос свежим не убиваем.
- **Никогда не роняет старт.** Обёртка `try/except` плюс `asyncio.wait_for(..., 5)`. При ошибке, например нет прав на `pg_terminate_backend`, пишется `WARNING` и старт продолжается.
- В лог пишется, сколько и каких сессий убрано.
- Если когда-нибудь будет деплой без простоя (две версии параллельно), уборщик закроет простаивающие соединения старой версии. Это безопасно: `pool_pre_ping=True` прозрачно переподключится.
- Права: в PostgreSQL обычная роль может завершать бэкенды **своей же** роли. На управляемом Timeweb это нужно проверить (см. §1.5).
- Отключается флагом `DB_REAP_ON_STARTUP=true|false` (по умолчанию `true`).

**Уровень 3: самоочистка на стороне сервера (закрывает дыры 1–3 даже без перезапуска)**

При открытии каждого соединения (событие `connect` у engine) выполнить `SET`:

| Параметр | Значение | Зачем |
|---|---|---|
| `idle_in_transaction_session_timeout` | `300s` | Зависшая транзакция не будет держать блокировки и слот вечно |
| `idle_session_timeout` (PG ≥ 14) | `pool_recycle + 300s` = 2100 с | «Сирота» после SIGKILL сама умрёт максимум через ~35 мин. Живому пулу это ничего не стоит: соединение старше 1800 с пул и так пересоздаёт (`pool_recycle`) |
| `tcp_keepalives_idle` / `_interval` / `_count` | `60` / `10` / `3` | Сервер обнаружит мёртвого клиента за ~1,5 мин, а не за 2 часа |

Важно: **не передавать эти параметры через `server_settings` asyncpg.** Если параметра нет в версии сервера (например `idle_session_timeout` на PG 13), соединение не откроется вовсе. Правильно: в событии `connect` проверить `server_version` и выполнить только поддерживаемые `SET`, каждый в своём `try`.

### 1.4. Настройки

```env
DB_POOL_SIZE=5
DB_MAX_OVERFLOW=0          # overflow на managed-БД не нужен: лимит должен быть жёстким
DB_CONNECTION_BUDGET=5
APP_INSTANCE=prod          # новое
DB_REAP_ON_STARTUP=true    # новое
```

Обновить `.env.example`, `docker-compose.yml` (проброс двух новых переменных), README и `test_config.py` (добавить тест «5/0/5 принимается»).

Почему 5 достаточно и почему `overflow=0`:
- Страница месячного плана при открытии шлёт около 6 параллельных запросов. Каждый запрос держит соединение **последовательно**: сначала коротко на авторизацию (отпускается до хендлера), потом на хендлер, потом на аудит. Одновременно занято не больше одного соединения на запрос. При пуле 2 запросы стояли в очереди, при 5 страница грузится почти без ожидания.
- После п. 3.4 (кеш сессий) авторизация перестаёт занимать соединение, и эффективная ёмкость пула для хендлеров вырастет ещё сильнее.
- Если в будущем появится `--workers N`, итоговый лимит будет **N × 5**. Бюджет нужно будет пересчитать, и в README это стоит записать явно.

### 1.5. Проверки перед включением (выполнить один раз в psql на проде)

```sql
SHOW server_version;                                   -- ≥14 → доступен idle_session_timeout
SHOW max_connections;                                  -- лимит тарифа
SELECT application_name, usename, state, count(*)
FROM pg_stat_activity GROUP BY 1,2,3 ORDER BY 4 DESC;  -- сколько сейчас занято и кем (видны ли «сироты»)
```

Порог: `5 (приложение) + 2–3 (psql, бэкапы, скрипты) + резерв` должен быть заметно меньше `max_connections`.

### 1.6. Наблюдаемость

- `GET /admin/db-status` (только для админа): снимок пула плюс сводка по `pg_stat_activity` для своего `application_name` по состояниям. Позволит видеть «сирот» без psql.
- Публичный `/health` ничего о `pg_stat_activity` не отдаёт: он без авторизации.

## 2. Уровни доступа: четыре уровня вместо трёх

### 2.1. Решение

Один упорядоченный уровень на раздел:

| Код | Значение | Название в UI | Разрешено |
|---|---|---|---|
| `none` | 0 | Нет доступа | Раздел скрыт в меню, API отвечает 403 |
| `view` | 1 | Просмотр | Чтение, выгрузки (Excel, скачивание файлов) |
| `edit` | 2 | Изменение | Создание и редактирование, **без удаления документов** |
| `full` | 3 | Полный | Всё, включая удаление и архивацию |

Почему упорядоченный уровень, а не отдельная галочка «удаление»:
- **Не бывает бессмысленных сочетаний.** С галочкой возможно «удаление без просмотра» или «удаление без изменения», и их пришлось бы отдельно запрещать и валидировать.
- **Проверка тривиальна:** `level(section) >= required`. Одно сравнение чисел.
- **UI проще:** одна строка на раздел, сегментированный переключатель из 4 позиций.
- Если когда-нибудь понадобится особая операция (например «проводить платежи»), её можно добавить как отдельный флаг рядом, не ломая модель.

### 2.2. Что считать «удалением», а что «изменением»

Правило: **удаление документа или справочной записи целиком — `full`. Удаление строки внутри документа, который пользователь и так редактирует, — `edit`.** Исключения, сохранённые ради совместимости с текущими правами, отмечены ⚠.

| Операция | Уровень |
|---|---|
| Удаление счёта, заказа, детали, прибора, версии спецификации, месячного плана, инвентаризации | `full` |
| Архивация детали или прибора (`PATCH …/archive`) | `full`: выводит запись из оборота, по смыслу это «мягкое удаление» |
| Удаление строк заказа, строк спецификации, псевдонимов прибора | `edit` |
| Отвязка счёта от строки плана, удаление файла из строки плана | `edit` |
| ⚠ Удаление строки «деталь в счёте» (`DELETE /invoices/{id}/parts/{link}`) | `full`: сейчас сотруднику это **запрещено** (есть тест), сохраняем |

### 2.3. Пресеты при выкатке (совпадают с текущим поведением)

| Раздел | `admin` | `employee` (как сейчас) |
|---|---|---|
| Месячные планы (с инвентаризацией) | суперпользователь | `full` |
| Счета от поставщиков | суперпользователь | `edit` |
| Детали | суперпользователь | `view` |
| Приборы | суперпользователь | `view` |
| Спецификации | суперпользователь | `view` |
| Заказы клиентов | суперпользователь | `view` |
| Статистика | суперпользователь | `view` |
| Загрузка спецификаций | суперпользователь | `none` |

Сверка с кодом: `employee_may_write` разрешает все записи в `/monthly-plans*`, это `full`. Записи в `/invoices*` кроме DELETE, это `edit`. Остальные GET разрешены, это `view`. `/imports/*` закрыт через `require_admin`, это `none`. Совпадает.

## 3. Производительность проверки прав

### 3.1. Сейчас

На каждый запрос: 1 SELECT (`user_sessions JOIN users`), и соединение сразу отпускается. Это уже сделано грамотно, ухудшать нельзя.

### 3.2. Уровень A (обязательный): права в том же SELECT

```sql
SELECT s.*, u.*, r.permissions, r.is_superuser, r.updated_at AS role_rev
FROM user_sessions s
JOIN users u ON u.id = s.user_id
JOIN roles r ON r.code = u.role           -- roles.code UNIQUE → поиск по индексу
WHERE s.token_hash = :h
```

- Добавочных обращений к БД **ноль**. JSONB с правами весит около 200 байт, задержка определяется сетью до удалённой БД, а не размером строки.
- Права **всегда актуальны**: изменение роли в админке действует со следующего запроса, перелогиниваться не нужно.

### 3.3. Уровень B (обязательный): предкомпилированная политика в памяти

- **Таблица правил «метод + URL → раздел + уровень»** (§4.4) компилируется **один раз при импорте модуля**: регулярки плюс индекс по первому сегменту пути (`/parts`, `/invoices`, …). Поиск правила — поиск в словаре и 1–5 проверок регулярок, то есть микросекунды.
- **Разбор прав роли** (JSONB → уровни + зависимые права чтения, §4.5) кешируется в `dict[(role_code, role_rev)] → Policy`. Когда роль меняется, меняется `updated_at`, поэтому устаревшая запись просто перестаёт находиться. **Инвалидация не нужна**, и это корректно даже при нескольких воркерах или инстансах. Размер ограничен (LRU на 64 записи), роли растут редко.

### 3.4. Уровень C (рекомендую, за флагом): TTL-кеш сессий

Это единственный способ сделать авторизацию **быстрее, чем сейчас**, а не просто не медленнее.

- `dict[token_hash] → (user_snapshot, policy, expires_at, last_used_at, cached_at)`, TTL = `AUTH_CACHE_TTL_SECONDS` (предлагаю 30 с; 0 = выключено).
- Попадание в кеш: **ни одного обращения к БД на авторизацию**. Экономится один сетевой round-trip до удалённой БД и одно занятие соединения из пула на каждый запрос. Страница планов с ~6 запросами получает −6 запросов к БД.
- Срок жизни сессии (`expires_at`) и скользящее продление (`_maybe_renew`) проверяются по кешированным данным. Продление пишет `UPDATE user_sessions SET … WHERE id = :id` не чаще раза в 30 мин, как сейчас.
- **Явное вытеснение из кеша** (обязательно, иначе дыра в безопасности):
  - выход (`/auth/logout`): удалить токен;
  - смена пароля, деактивация, удаление, смена роли пользователя: удалить все токены этого `user_id`;
  - изменение или удаление роли: удалить все записи с этим `role_code` (или просто очистить кеш целиком, это дёшево).
- Процесс сейчас **один** (нет `--workers`), поэтому вытеснение точное и мгновенное. Если появятся несколько воркеров, в худшем случае изменения дойдут до других воркеров за TTL (30 с). Это надо записать в README рядом с предупреждением о `--workers`.
- Размер ограничен (например 1000 токенов, LRU).
- Порядок внедрения: сначала уровни A и B, замер, затем C с `AUTH_CACHE_TTL_SECONDS=30`.

**Что кешируется, а что нет (важно для понимания)**
- Кешируется **только результат авторизации**: кто пользователь, активен ли он, какая у него роль и права.
- **Данные не кешируются.** Планы, счета, детали, заказы, спецификации, статистика, файлы по-прежнему читаются из БД на каждом запросе. Изменения других пользователей видны при следующем обновлении страницы, как сейчас.

**Где возможна задержка до TTL (30 с) и почему это приемлемо**

| Ситуация | Задержка |
|---|---|
| Выход, смена пароля, деактивация, удаление, смена роли пользователя, правка или удаление роли **через админку** (один процесс бэкенда, как сейчас) | **Нет**, записи вытесняются сразу |
| Изменение пользователей или ролей **напрямую в БД** (psql), в обход API | До 30 с |
| Несколько воркеров (`--workers`) или несколько инстансов бэкенда | До 30 с в остальных процессах |
| Меню и кнопки на фронте у пользователя с уже открытой вкладкой | Не связано с кешем: обновляются при перезагрузке страницы или первом 403 (§4.3 п. 12) |

Если в будущем появятся несколько воркеров и задержка станет неприемлемой, есть два варианта: снизить TTL (например до 10 с) или добавить «эпоху авторизации» (счётчик в БД, который меняется при любой правке прав). Сейчас это не нужно.

**Что входит в работу (≈ 0,5 дня, БД не меняется)**
1. Модуль кеша: словарь с TTL и LRU, методы `get`, `put`, `evict_token`, `evict_user(user_id)`, `evict_role(role_code)`, `clear()`.
2. Встраивание в `auth_middleware`: промах → текущий SELECT (уровень A) → положить в кеш; попадание → без обращения к БД. Проверка `expires_at` и `is_active` выполняется в обоих случаях.
3. `_maybe_renew` при попадании в кеш: точечный `UPDATE user_sessions … WHERE id = :id` не чаще раза в `SESSION_IDLE_RENEW_MINUTES`, с обновлением `last_used_at` в кеше.
4. Точки вытеснения: `logout`, `update_user` (пароль, `is_active`, `role`, `username`), `delete_user`, PATCH и DELETE `/admin/roles/{id}`.
5. Настройка `AUTH_CACHE_TTL_SECONDS` (по умолчанию `0` = выключено) в `config.py`, `.env.example`, `docker-compose.yml`, README. В README предупредить про задержку при `--workers`.
6. Тесты: старый токен перестаёт работать **сразу** после выхода, смены пароля, деактивации и удаления; смена роли или прав применяется со следующего запроса; с TTL=0 поведение идентично текущему; просроченная сессия не оживает из кеша.
7. Замер p50/p95 по логам `duration_ms` до и после включения.

**Откат:** `AUTH_CACHE_TTL_SECONDS=0` и перезапуск, без изменения кода.

### 3.5. Как замерить эффект

В логах уже есть `duration_ms` на каждый запрос (`LOG_REQUESTS=true`). Сравнить p50/p95 для `GET /auth/me` и `GET /monthly-plans/{id}/parts-with-coverage` до и после. Ожидание: уровни A и B дают «так же, как сейчас», уровень C даёт минус одну сетевую задержку до БД на каждом запросе.

## 4. Редактор ролей: модель, API, защита

### 4.1. Изменения БД (только добавление, откат безопасен)

```sql
-- backend/sql/2026-10-XX_roles.sql (идемпотентный, по образцу 2026-08-20_inventory.sql)
SET lock_timeout = '5s';
BEGIN;

CREATE TABLE IF NOT EXISTS roles (
    id           SERIAL PRIMARY KEY,
    code         VARCHAR(32)  NOT NULL UNIQUE,       -- то, что лежит в users.role; неизменяем
    name         VARCHAR(128) NOT NULL,
    description  TEXT,
    is_system    BOOLEAN NOT NULL DEFAULT false,     -- системную роль нельзя менять и удалять
    is_superuser BOOLEAN NOT NULL DEFAULT false,     -- обходит все проверки; только у admin
    permissions  JSONB   NOT NULL DEFAULT '{}'::jsonb,
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE UNIQUE INDEX IF NOT EXISTS uq_roles_name_ci ON roles (lower(name));

INSERT INTO roles (code, name, is_system, is_superuser, permissions) VALUES
  ('admin', 'Администратор', true, true, '{}'),
  ('employee', 'Сотрудник', false, false,
   '{"monthly_plans":"full","invoices":"edit","parts":"view","devices":"view",
     "bom":"view","orders":"view","statistics":"view","import":"none"}')
ON CONFLICT (code) DO NOTHING;

-- Защита «роль с пользователями нельзя удалить» на уровне БД (страховка к проверке в API)
DO $$ BEGIN
  IF NOT EXISTS (SELECT 1 FROM pg_constraint WHERE conname = 'fk_users_role_roles') THEN
    ALTER TABLE users ADD CONSTRAINT fk_users_role_roles
      FOREIGN KEY (role) REFERENCES roles(code) ON UPDATE CASCADE ON DELETE RESTRICT NOT VALID;
    ALTER TABLE users VALIDATE CONSTRAINT fk_users_role_roles;
  END IF;
END $$;

COMMIT;
```

Решения и почему:
- **`users.role` остаётся строкой** (код роли), без `role_id`. Старый код продолжит работать с `admin`/`employee`, откат — просто деплой предыдущего коммита. Таблица `roles` и FK старому коду не мешают.
- **Права хранятся в JSONB, а не отдельной таблицей `role_permissions`.** Разделов 8, права всегда читаются целиком, одна строка = одно чтение. Схема ключей валидируется Pydantic на входе API (неизвестные ключи отбрасываются, отсутствующие = `none`).
- **`NOT VALID` + `VALIDATE`** — две фазы, чтобы не держать тяжёлую блокировку на `users`. `lock_timeout 5s` взят как в скрипте инвентаризации.
- То же самое дублируется в `schema_ensure.py`: создание таблицы, засев двух ролей и FK с проверкой существования (по образцу `_ensure_bom_subdev_unique`). **Порядок в lifespan: засев ролей → `ensure_default_users()`**, иначе на чистой БД FK не даст создать пользователей.
- `ensure_default_users()` и `init_data.py` используют коды `admin`/`employee`, которые уже засеяны. Изменений не требуется, только порядок вызова.

Код новой роли генерирует сервер: `r_` + 8 hex-символов. Пользователь вводит только название. Код неизменяем, поэтому переименование роли никого не затрагивает.

### 4.2. API (все под `/admin/*` → только суперпользователь)

| Метод | Путь | Поведение |
|---|---|---|
| GET | `/admin/roles` | Список ролей со счётчиком пользователей |
| GET | `/admin/roles/sections` | Справочник разделов и уровней с подписями (фронт не хардкодит список) |
| POST | `/admin/roles` | Создать: `name`, `description`, `permissions` |
| PATCH | `/admin/roles/{id}` | Изменить. Для системной роли → 403 |
| DELETE | `/admin/roles/{id}` | Удалить. Системная → 403; есть пользователи → **409** со списком логинов |
| POST | `/admin/roles/{id}/copy` | Копия роли (удобно делать новую из «Сотрудника») |

`GET /auth/me` дополнительно возвращает `role_name`, `is_superuser`, `permissions` (явные уровни по разделам, для меню и кнопок).

### 4.3. Защита: полный перечень

**Роли**
1. Роль `admin`: `is_system=true, is_superuser=true`. PATCH и DELETE → 403 «Системная роль не редактируется».
2. Флаг `is_superuser` **не принимается** из API ни при создании, ни при изменении. Второй «админ-роли» создать нельзя.
3. Удаление роли с пользователями → 409 (проверка в API плюс FK `ON DELETE RESTRICT` в БД как страховка от гонки).
4. Название уникально без учёта регистра, код неизменяем.
5. Назначение несуществующей роли пользователю → 400. `normalize_role()` проверяет по таблице `roles`, а не по константе `VALID_ROLES`.

**Пользователи.** В текущем коде найдено слабое место: `PATCH /admin/users/{id}` позволяет админу понизить себя или деактивировать последнего админа, и тогда систему можно потерять целиком.

6. Нельзя сменить роль самому себе и нельзя деактивировать самого себя.
7. Нельзя понизить или деактивировать **последнего активного** админа. Сейчас `delete_user` считает всех админов, включая неактивных, это тоже исправить на `is_active = true`.
8. Смена роли пользователя: сессии не отзываются (права и так читаются на каждом запросе), но из кеша п. 3.4 записи вытесняются.

**Доступ по прямой ссылке**
9. **Бэкенд — единственный источник истины.** Middleware проверяет каждый запрос по таблице правил §4.4. Скрытый раздел по прямому URL API всё равно отдаёт 403.
10. **Запрет по умолчанию.** Сейчас любой GET на любой путь разрешён всем авторизованным. В новой схеме путь без правила для не-админа → 403. Это защищает будущие эндпоинты, которые забыли разметить.
11. **Тест покрытия маршрутов** (по образцу `test_db_transaction_scope`): перебрать `app.routes` и убедиться, что у каждого (кроме публичных и `/auth/*`) есть правило. Новый эндпоинт без правила роняет CI.
12. **Фронт** (для удобства, не для безопасности):
    - `lib/permissions.ts`: карта «маршрут страницы → раздел» и store `can(section, level)`.
    - `+layout.svelte`: после `me()` и на каждой клиентской навигации проверяет текущий маршрут. Нет доступа → экран «Нет доступа к разделу» со ссылкой на первый доступный раздел (не редирект, чтобы не было петель и было понятно, что случилось).
    - Меню строится по правам: раздел `none` не показывается, группа «Производство» или «Финансы» без доступных пунктов скрывается целиком.
    - **Стартовая страница:** сейчас `/` и логин жёстко ведут на `/monthly-plans`. Нужно вести на первый доступный раздел, иначе у роли без планов вход закончится экраном «нет доступа».
    - `/admin` доступен только при `is_superuser`.
    - Ответ 403 от API во время работы → перечитать `me()` (права могли поменяться) и показать уведомление.
13. **Аудит:** создание, изменение и удаление роли пишется в `audit_logs.details` с разницей прав («Счета: view → edit»). Смена роли пользователя тоже пишется с «было → стало».

### 4.5. Зависимые права чтения (иначе страницы ломаются)

Страницы читают данные соседних разделов. Без этого роль «только Планы» получит сломанную страницу планов. Правило: **раздел даёт право только на ЧТЕНИЕ конкретных эндпоинтов-справочников, которые нужны его странице. В меню эти разделы не появляются. Запись по зависимостям не даётся никогда.**

| Раздел (≥ view) | Дополнительно разрешено читать | Кто это использует на фронте |
|---|---|---|
| monthly_plans | `GET /devices` (список), `GET /parts` (список), `GET /invoices/**` | monthly-plans: `devices.list`, `parts.list`, `invoices.list/get/files/parts` |
| invoices | `GET /monthly-plans` (только список), `GET /parts` (список), `GET /files/{id}/download` | invoices: `monthlyPlans.list`, `parts.list` |
| orders | `GET /devices` (список), `GET /parts` (список), `GET /devices/{id}/bom` | orders: `devices.list`, `parts.list`, `bom.list` |
| bom | `GET /devices` (список), `GET /parts` (список) | bom: `devices.list`, `parts.list` |

Следствие для UI: на странице планов создание и правка счёта (`invoices.create/update`) показываются, только если у роли `invoices ≥ edit`. У пресета «Сотрудник» так и есть (`edit`), поэтому для текущих пользователей ничего не меняется.

Осознанный компромисс: роль «только Счета» через API сможет прочитать **список** месячных планов (без строк). Это нужно для привязки счёта к плану и приемлемо.

### 4.6. Фронтенд: объём

1. **Админка → вкладка «Роли»:** таблица ролей (название, число пользователей, системная), редактор: название, описание и матрица «раздел × уровень» (сегментированный переключатель на 4 позиции, сгруппированный как меню: Производство / Финансы / Планы). Кнопки «Копировать» и «Удалить» (неактивна, если есть пользователи; всплывающая подсказка со списком). У системной роли редактор только для чтения с плашкой «Системная».
2. **Форма пользователя:** вместо жёсткого выбора admin/employee — список ролей из `/admin/roles`. Подписи ролей в таблице пользователей и в шапке берутся из `role_name` (сейчас `roleLabel()` знает только две роли).
3. **Типы в `api.ts`:** `role: string`, плюс `role_name`, `is_superuser`, `permissions`.
4. **Меню, защита маршрутов, стартовая страница** (§4.3 п. 12).
5. **Режим «только просмотр» на страницах.** Скрыть кнопки создания, правки и удаления по `can()`: детали, приборы, спецификации, заказы, счета, планы. Сейчас кнопки видны всем и сотрудник получает 403 при нажатии. После этой работы интерфейс перестанет «обманывать». Отдельно `delete` скрывается при `edit`, но не `full`.

## 6. Решения, принятые по умолчанию (можно переиграть до старта)

1. Архивация детали или прибора = `full` (как удаление). Альтернатива: `edit`, если архивацию нужно дать «редакторам».
2. Удаление строки детали в счёте = `full` (сохраняем текущий запрет для сотрудника). Альтернатива: `edit`, как для остальных строк документов.
3. Запись по зависимостям не даётся никогда, только чтение.
4. Полный дамп БД (`/imports/db/dump`) — только суперпользователь, в роли не выносится.
5. Инвентаризация входит в раздел «Месячные планы». Если нужно разграничивать отдельно, это ещё один ключ раздела, модель не меняется.
6. Одна роль на пользователя (не набор ролей). Для этого масштаба проще и прозрачнее, а копирование ролей закрывает потребность в «почти такой же роли».

## 7. Замечено попутно (вне задачи, но важно)

- **Прод работает по HTTP** (`http://147.45.158.42`): пароли и токены идут по сети открытым текстом. Нужен HTTPS (домен + Let's Encrypt в nginx). Это важнее всего остального в этом разделе.
- В README пароли по умолчанию `admin/admin`, `employee/employee`. Стоит убедиться, что на проде они сменены, и убрать их из README.
- Защита логина от перебора (`login_guard`) живёт в памяти процесса. При одном воркере это нормально, но при перезапуске счётчики сбрасываются.
- `GET /files/{id}/download` не проверяет, к какому документу относится файл: зная id, можно скачать любой файл. С новыми правами доступ хотя бы ограничится ролями со счетами или планами. Полноценная проверка принадлежности — отдельная задача.
- Параметр `S3_*` в `.env` не используется (файлы в PostgreSQL). Это не баг, но место для путаницы.
